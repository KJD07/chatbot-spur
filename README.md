# Spur AI Live Chat

A full-stack AI-powered customer support chat widget for Spur Store, a fictional e-commerce brand. Built as an assignment to demonstrate end-to-end product engineering with a modern TypeScript stack.

---

## Project Overview

Spur Chat is a single-page support widget where users can ask questions about shipping, returns, and store policies. Messages are persisted in a SQLite database; the AI replies are generated by an OpenRouter-hosted LLM and streamed back through an Express API. Sessions survive page refreshes via localStorage. The app runs fully containerised with Docker Compose for development and a multi-stage production build for deployment.

## Local Development Setup

### Prerequisites
- Docker & Docker Compose installed
- An [OpenRouter](https://openrouter.ai) API key

### Steps

```bash
# 1. Clone the repo
git clone <your-repo-url> && cd spur-chat

# 2. Create the backend env file (required — without this the backend won't start)
cp backend/.env.example backend/.env
# Edit backend/.env and set your OPENROUTER_API_KEY

# 3. Build and start both containers
docker-compose up --build

# 4. Run database migrations (first time only — open a second terminal)
docker-compose exec backend npx prisma migrate dev --name init

# 5. (Optional) Seed the database with sample data
docker-compose exec backend npx ts-node prisma/seed.ts
```

The app is now running:
- **Frontend** → http://localhost:5173
- **Backend API** → http://localhost:4000
- **Health check** → http://localhost:4000/health

### Environment Variables

| Variable | Location | Description |
|---|---|---|
| `OPENROUTER_API_KEY` | `backend/.env` | Your OpenRouter API key |
| `PORT` | `backend/.env` | Backend port (default: 4000) |
| `DATABASE_URL` | `backend/.env` | SQLite path (default: `file:./dev.db`) |
| `VITE_API_URL` | `frontend/.env` | Backend URL seen by the browser (default: `http://localhost:4000`) |

## Architecture

```
Browser
  │
  ├─── Static assets (HTML/CSS/JS)
  │       └──> Vite dev server (port 5173 in dev)
  │            nginx:alpine (port 80 in prod)
  │
  └─── API calls  POST /chat/message
                  GET  /chat/history/:id
                       │
                       ▼
              Express (Node.js, port 4000)
                  │            │
                  ▼            ▼
              SQLite       OpenRouter API
            (via Prisma)   (openai/gpt-4o-mini)
```

### Request flow

1. User types a message in the React frontend.
2. `sendMessage()` in `api.ts` posts to `POST /chat/message` with the current `sessionId` (or null for a new session).
3. The Express route validates the body with Zod, creates a Conversation row if needed, persists the user Message, then fetches the last 10 messages to build LLM context.
4. `generateReply()` in `llm.ts` calls OpenRouter's `/v1/chat/completions` endpoint using the `openai` SDK with a custom `baseURL`.
5. The AI reply is persisted as a second Message row, then returned to the frontend as `{ reply, sessionId }`.
6. The frontend appends the AI message and stores the sessionId in localStorage for history restoration.

---

### Extensibility

The architecture is designed to support multiple channels (WhatsApp, Instagram, Facebook) without major changes:

- **New channels** → add a new route file (e.g. `routes/whatsapp.ts`) that validates the incoming webhook, extracts the message, and calls the same `generateReply()` function from `llm.ts`.
- **New tools/integrations** → `llm.ts` is fully encapsulated; swap models or add tool-calling without touching routes or DB logic.
- **Channel tracking** → the `Conversation` model includes a `channel` field (`"web"` | `"whatsapp"` | `"instagram"`) so conversations are always traceable to their source.

## LLM Notes

**Provider:** [OpenRouter](https://openrouter.ai) — a single API key gives access to many models without per-provider accounts.

**Model:** `openai/gpt-4o-mini` — chosen for low latency and cost; sufficient for FAQ-style support replies.

**System prompt:** Instructs the model to act as a Spur Store support agent and provides the store's key facts (shipping times, free-shipping threshold, return policy, support hours). Keeping the facts in the system prompt rather than retrieved from a DB keeps the demo simple without sacrificing accuracy.

**History window:** The last 10 messages of the conversation are included with every request. This gives the model enough context for multi-turn follow-ups while keeping token usage bounded.

**Truncation:** User messages over 2000 characters are truncated server-side before being sent to the LLM; a note is appended to the system prompt so the model knows the message was cut.

## Trade-offs & "If I Had More Time"

1. **SQLite → PostgreSQL.** SQLite is zero-config and perfect for this demo, but it stores the database as a single file on disk. On ephemeral platforms like Railway the file is lost on redeploy. In production I would switch to a hosted Postgres instance (Railway provides one natively) with zero code changes thanks to Prisma's provider abstraction.

2. **Polling vs. streaming.** Replies are returned as a single JSON response after the LLM finishes. Adding Server-Sent Events or WebSocket streaming would make replies feel much faster by showing tokens as they arrive — a significant UX improvement for longer answers.

3. **Authentication.** Sessions are identified by a random cuid stored in localStorage. Anyone who knows a sessionId can read that conversation. A proper auth layer (JWT + user accounts) would scope history to verified users.

4. **Rate limiting & abuse protection.** The API currently has no per-IP rate limit. A simple express-rate-limit middleware would prevent the OpenRouter key from being abused in a shared deployment.

5. **Test coverage.** The project ships with zero automated tests. I would add unit tests for `generateReply` (mocking the OpenAI client) and `POST /chat/message` (mocking Prisma) with Jest, plus a Playwright smoke test for the send-and-reply flow in the browser.

## Production Docker Build

```bash
# Build and run the production stack
docker-compose -f docker-compose.prod.yml up --build

# Frontend served at http://localhost:80
# Backend API at http://localhost:4000
```

The production build uses:
- **Backend:** multi-stage Node build — TypeScript compiled to JS in a builder stage, only production `node_modules` copied to the final image. Prisma migrations run automatically on container start.
- **Frontend:** Vite builds static files in a builder stage; nginx:alpine serves them and proxies `/chat/*` to the backend, so the browser only ever talks to a single origin.

## Deployment on Railway

### Step 1 — Push to GitHub
```bash
git init && git add . && git commit -m "Initial commit"
git remote add origin <your-github-repo>
git push -u origin main
```

### Step 2 — Create Railway project
1. Go to [railway.app](https://railway.app) → **New Project** → **Deploy from GitHub repo**.
2. Select your repository.

### Step 3 — Backend service
1. Railway auto-detects the repo. Click **Add Service** → **GitHub Repo** and set the **Root Directory** to `/backend`.
2. Set build command: `docker build -f Dockerfile --target production .`
3. Set start command: leave blank (CMD in Dockerfile handles it).
4. Add environment variables:
   - `OPENROUTER_API_KEY` = your key
   - `PORT` = `4000`
   - `DATABASE_URL` = `file:./dev.db`
   - `NODE_ENV` = `production`
5. Note the generated Railway backend URL (e.g. `https://spur-backend.up.railway.app`).

> **SQLite limitation on Railway:** Railway's filesystem is ephemeral — the `.db` file is wiped on each redeploy. For this assignment this is acceptable (history is lost on redeploy). For a production app, provision a Railway Postgres plugin and update `DATABASE_URL` and the Prisma provider to `postgresql`.

### Step 4 — Frontend service
1. Add another service → same repo, **Root Directory** `/frontend`, **Dockerfile** `Dockerfile.prod`.
2. Add build argument:
   - `VITE_API_URL` = `https://spur-backend.up.railway.app` (your backend Railway URL)
3. Expose port 80.

### Step 5 — Update nginx proxy
If you set `VITE_API_URL` as a build arg, the frontend bakes the backend URL into the bundle. The nginx proxy (`/chat/` → `backend:4000`) works out of the box in the Docker Compose prod setup but on Railway the two services are separate containers — the `backend` hostname won't resolve. In that case, make sure `VITE_API_URL` is set correctly and the browser will call the backend Railway URL directly.

### Step 6 — Verify
Visit your frontend Railway URL → send a message → confirm an AI reply comes back.
